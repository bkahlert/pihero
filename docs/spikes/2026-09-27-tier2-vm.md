# Spike: tier-2 QEMU VM (Raspberry Pi OS rootfs, Debian kernel)

Host: macOS, QEMU 11.1.1 (Homebrew), podman 6.1.2 with `podman-machine-default` (applehv, arm64, see [the tier-1 spike](2026-09-27-tier1-podman.md)).
Seven QEMU launches were made: one that failed in the initramfs, two with the brief's user-data as written, one with a `write_files` variant, a reboot of that VM, and two with the fixes from `Adjustments for Task 10` applied. Every value below was observed in one of them.

## Loop devices in privileged podman

Two things went wrong with the brief's container commands. First, `podman build` without `--platform` reused the arm/v7 `debian:trixie-slim` left behind by the tier-1 spike and printed `WARNING: image platform (linux/arm/v7) does not match the expected platform (linux/arm64)`; `podman build --platform linux/arm64` fixed it. Second, `losetup --find --show --partscan` inside `podman run --privileged` failed:

```
losetup: /cache/spike/raspios.img: failed to set up loop device: No such file or directory
losetup: device node /dev/loop0 (7:0) is lost. You may use mknod(1) to recover it.
```

podman populates the container's `/dev` once at start; the node `loop-control` creates on the machine and the `p1`/`p2` partition nodes never appear inside. Adding `-v /dev:/dev` to `podman run` fixed it: `/dev/loop0`, `/dev/loop0p1` (259,0) and `/dev/loop0p2` (259,1) appeared, `mount` of the ext4 and vfat partitions worked, and the `debugfs` fallback was not needed. The whole Step 2 script (losetup to `rootfs.qcow2`) took 64 s on the virtiofs-mounted `~/.cache/pihero`: `mkfs.ext4 -d` 51 s, `qemu-img convert` 2 s. Decompressing the image took about 40 s.

## Kernel install in chroot

`apt-get install -y -q --no-install-recommends linux-image-arm64` in the chroot installed `linux-image-6.12.107+deb13-arm64` (6.12.107-1, 92.9 MB) and the metapackage with exit 0. Both Raspberry Pi hooks skip Debian's kernel and do not fail, so no fix was needed:

`file vmlinuz`: `Linux kernel ARM64 boot executable Image, little-endian, 4K pages` (uncompressed, 37,660,608 bytes). Version string from the boot log: `Linux version 6.12.107+deb13-arm64 (debian-kernel@lists.debian.org) (aarch64-linux-gnu-gcc-14 (Debian 14.2.0-19) 14.2.0, GNU ld (GNU Binutils for Debian) 2.44) #1 SMP Debian 6.12.107-1 (2026-08-29)`.
The initrd the hook generated does not boot QEMU: Raspberry Pi OS ships `MODULES=dep` in `/etc/initramfs-tools/initramfs.conf`, so the 12,175,879-byte initrd (484 entries) contained `virtio_mmio.ko.xz` but no `virtio_blk` (`CONFIG_VIRTIO_BLK=m`, `CONFIG_VIRTIO_NET=m`; `CONFIG_VIRTIO_PCI=y`). The first boot ended after 30 `local-block` rounds with `ALERT!  LABEL=rootfs does not exist.  Dropping to a shell!`. Fix: `printf 'MODULES=most\n' > /etc/initramfs-tools/conf.d/pihero-qemu.conf` in the rootfs, then `chroot /mnt/root update-initramfs -u -k 6.12.107+deb13-arm64` (exit 0, same `Unsupported initramfs version` warning). The initrd grew to 37,978,765 bytes and the root filesystem was found.

## Decision

Go with the Raspberry Pi OS rootfs. It boots to SSH in 7 s under hvf with Debian's 6.12 kernel, the `bootfs` FAT image mounts at `/boot/firmware` by label and seeds cloud-init, and apt installs from the Mac. The Pi-specific packaging the tier is meant to exercise (`rpi-cloud-init-mods`, `userconf-pi`, the `raspi-firmware` kernel hooks, `rpi-eeprom-update`, `rpi-usb-gadget`, the rpt `bluez` build) is present and behaves observably; Debian's cloud image would have none of it. The deviations needed are mechanical and listed below. The fallback was not evaluated because the brief's path reached SSH well inside the time box.

## Adjustments for Task 10

1. Tools image: build with `podman build --platform linux/arm64`. Run `prepare-rootfs` with `podman run --privileged -v /dev:/dev …`; without `-v /dev:/dev`, `losetup` fails as quoted above.
2. `prepare-rootfs`, after the kernel install: write `MODULES=most` to `/etc/initramfs-tools/conf.d/pihero-qemu.conf` in the rootfs and run `chroot "$root" update-initramfs -u -k <version>` (the version is the `+deb13-arm64` directory under `/lib/modules`). Expect an initrd of about 38 MB; the 12 MB one drops to an `(initramfs)` shell. Kernel installed: `linux-image-arm64` 6.12.107-1, binary package `linux-image-6.12.107+deb13-arm64`, `vmlinuz` an uncompressed `Image`.
3. `prepare-rootfs`: mask `rpi-eeprom-update.service` (`ln -s /dev/null "$root/etc/systemd/system/rpi-eeprom-update.service"`); it is the only failed unit and fails on a shell arithmetic error without EEPROM hardware. The `cloud-init-local.service.d/pihero-bootfs.conf` drop-in may stay or go; `rpi-cloud-init-mods` already orders `cloud-init-main.service` after `/boot/firmware`.
4. `prepare-rootfs`: write `/etc/cloud/cloud.cfg.d/90_pihero_tier2.cfg` with exactly these two lists (the stock lists with `apt_configure` added and `netplan_nm_patch` removed):

5. Device `user-data`: add `preserve_sources_list: true` under `apt:`; keep `sources: pihero-local: source: deb [trusted=yes] http://10.0.2.2:8000/ ./`. Do not set `rpi: enable_usb_gadget: true` in tier-2 device files; it always fails on `linux,dummy-virt` and turns the status into `degraded done`. With items 3 to 5 applied, `cloud-init status --wait --long` exits 0 and `systemctl --failed --no-legend --plain` prints nothing, so the plan's `wait_provisioned` (raise on non-zero) and `test_no_unit_failed` hold as written. Without them the exit code is 2 (`extended_status: degraded done`, `errors: []`).
6. `cmdline.txt` substitutions: drop every `root=`, `console=` and `init=` word (the stock line has `console=serial0,115200` and `console=tty1`), prepend `root=LABEL=rootfs console=ttyAMA0,115200`, keep the rest. Also drop `resize`: the boot works with it, but the rpt `resize_early` script prints two `cat: can't open '/sys/block//vda/partition'` errors on the serial console. Result for the stock file: `root=LABEL=rootfs console=ttyAMA0,115200 rootfstype=ext4 fsck.repair=yes rootwait` (derived; every boot in this spike still carried `resize`).
7. `SSH_OPTS` must include `-o IdentitiesOnly=yes` next to `-i`, or an ssh-agent with several keys makes every attempt fail with `Too many authentication failures`.
8. Timeouts: SSH answered 7 s after launch on every boot and cloud-init finished in under 5 s, so a 120 s `wait_ssh` and 900 s `wait_provisioned` are ample. The one failure mode seen, the initramfs giving up on the root device, never opens port 22 and so surfaces as the `wait_ssh` timeout; the serial log then ends in `ALERT!  LABEL=rootfs does not exist.  Dropping to a shell!`.
9. `bootfs`: `mkfs.vfat -n bootfs -C <img> 65536` plus `mcopy` produced an image that systemd mounts by `LABEL=bootfs`; the lowercase-label warning is harmless. `test_boot_partition_is_the_bootfs_image` can check `findmnt -no SOURCE /boot/firmware` is `/dev/vdb` and that `/boot/firmware/user-data` exists.
10. `apt-cache policy | grep 10.0.2.2` only lists the source once the repo contains at least one package; the harness's repo always does, so the check is fine there, but an empty repo must not be used as a smoke test.
11. Watchdog: with the brief's QEMU command there is no `/dev/watchdog`, yet the manager reports `RuntimeWatchdogUSec=1min` in the VM (unlike the container's `0` in the tier-1 spike). `TestWatchdog::test_is_armed` needs a watchdog device QEMU does not provide here; that was not investigated.

## Checkpoint

Task 15 of [the plan](../superpowers/plans/2026-09-27-pihero-2-foundation.md), run on 2026-09-28 against a
Raspberry Pi Zero 2 W Rev 1.0 with the 2026-09-15 Raspberry Pi OS Lite 64-bit (Trixie) image, on Wi-Fi and
on the USB gadget port of a Mac running macOS 27. The card was written by `make flash`, the packages came
from the published `2.0.0~rc.2` repository.

**Result.** Every item of the checklist holds once the device file has the fixes below: `Checkpoint` is
advertised on `_device-info._tcp` with `model=AirPort4` and `machine=Raspberry Pi Zero 2 W Rev 1.0`, SSH
on `_ssh._tcp`, the MOTD lists both packages, `cloud-init status` is `done` (degraded only by Raspberry
Pi OS's own missing `cc_netplan_nm_patch`), no failed units, no `Unsupported key`,
`RuntimeWatchdogUSec=15s`, `USB Gadget (shared)` exists, and `uv run pytest -m installed --target=ssh`
passes 12 tests and skips the 4 mutating ones. Provisioning takes about 4 min 15 s from power-on with two
reboots (interface settings, then the gadget); a booted Pi answers SSH about 70 to 90 s after power-on.

**What the first attempt exposed**, all in Raspberry Pi OS or its interplay with cloud-init, none in the
packages:

1. `rpi: enable_usb_gadget: true` never works on a fresh card: cloud-init runs `rpi-usb-gadget on -f` with
   a 15 s timeout and the script waits 5 + 10 s for a `usb0` that only exists after a reboot. The module
   aborts, the rest of `rpi:` is skipped, no reboot is requested. Fix: enable the gadget from `runcmd` and
   set `/run/reboot-required` for `power_state`.
2. Wi-Fi does not come up on the first boot unless `cfg80211.ieee80211_regdom=` is already on the kernel
   command line. netplan writes it there during that boot (through Raspberry Pi's patched libnetplan
   calling `raspi-config do_wifi_country`), too late: NetworkManager-wait-online gives up, cloud-init's final
   stage runs without a network, apt installs nothing. With the domain on the command line wlan0 connected
   at 68 s and the final stage waited for it. Fix: `make flash` writes it, as Imager does.
3. macOS 27 binds `g_ether`'s RNDIS configuration and never passes a frame. Fix: `g_cdc` (CDC ECM, plus an
   ACM serial port the host sees as `/dev/tty.usbmodem*`). Windows has no inbox ECM driver; a configfs NCM
   gadget would serve all three hosts and belongs in a `pihero-usb-gadget` package.
4. macOS asks for DHCP only while the link comes up, then settles for a self-assigned address. The module
   loaded at 10 s, NetworkManager served at 25 s. Fix: `usb-gadget.service`, `After=NetworkManager.service`,
   loads the module.
5. macOS creates a network service per host MAC, and `g_cdc` picks random MACs. Fix: the unit derives both
   MACs from the board serial; the gadget is named like upstream's (`Raspberry Pi USB Gadget`).
6. A fresh card installs nothing. Its clock starts at the image build date, the interfaces reboot comes
   before NTP has synced, and in the next boot cloud-init's final stage runs `apt-get update` before
   systemd-timesyncd steps the clock: sqv rejects every `InRelease` as "not live yet", the pihero repository
   counts as unsigned, and the later reboot resets `cloud-init status` to `done` without errors. The
   re-provisioning runs above never saw it because their saved clock was recent; only the clean reflash did.
   Fix: `bootcmd` orders `cloud-final.service` after `time-sync.target` and enables `systemd-time-wait-sync`.
   A wait in `bootcmd` itself only burns its timeout: with the NoCloud seed in local mode the init modules
   run in the pre-network stage.

Also learned: Raspberry Pi OS keeps the journal volatile even with `/var/log/journal` present, so a first
boot's NetworkManager log is only available if `runcmd` copies it to the boot partition; the card's ext4
root can be read on the Mac with `debugfs -c` in the tools container from a `dd`-style dump obtained through
`authopen` (see `testkit/src/pihero_testkit/flash.py` for the descriptor passing).

git-derived one, which only matches at a tag.
